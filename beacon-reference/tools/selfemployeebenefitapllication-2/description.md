# selfEmployeeBenefitApllication

**Task:** Self Employee Benefit Application

**Tags:** Benefits, phase3

**Status:** live

## Description

Applies for a benefit for the signed-in employee themselves. FIRST ACTION for any request to apply or claim a benefit for oneself ("apply benefit to me", "claim my medical bills"): call this tool at once with no arguments - write nothing, ask nothing and call no other tool before it (not getApplicationStructure, selfBenefitApplicationTypes, getBenefitApplicationTypesDetails, employeeBenefitApplication, getAdminInformationDetails or dateFormat). It identifies the employee itself and returns the benefit types they may apply for - show only those. Then call with benefitType, then with fieldValues, asking only for what the tool returns. The application date is always required; every figure is calculated for it. Always previews first and submits only with confirmed:true plus that preview's previewDigest. Chat attachments are validated and uploaded at preview, removable before confirming. For a subordinate, use myTeamBenefitApplication.

## Signature

```
selfEmployeeBenefitApllication
```

## Arguments

_None._


## Advanced arguments

- `benefitType` (string, optional) — The benefit type to apply for, named as the user says it (e.g. 'Medical Claims'). Never ask the user to name a benefit type before you have called this tool, and NEVER offer types from your own knowledge (Health Insurance, Life Insurance, Cash Benefit and the like are not real options here) - the types differ per employee and per company. When the user has not named one, call this tool with benefitType omitted and it returns their own live availableBenefitTypes; show the user exactly that list and ask which one. Never use masterDataTypes to get the types - it lists HR admin master-data categories, not what an employee may apply for, and refuses anyone without admin access. If the name they give is not on it, or matches more than one, the tool returns the candidates to choose from. Never ask for a code. This tool is for the signed-in user's OWN application and identifies them itself - never ask who they are, and never ask for an employee number or employee ID. To apply on behalf of one of their subordinates, use myTeamBenefitApplication instead.
- `fieldValues` (object, optional) — For benefit types built from plain fields: the values, keyed by each field's exact displayName from this tool's own discovery response. Call with benefitType set and fieldValues omitted first to get that list with each field's mandatory flag, input type and options, then ask the user only for those fields. Never ask for fields you have imagined (benefit plan, policy number and so on): they differ per benefit type and per employee, and only the discovery response is real. The application date is always required even when it says not-mandatory, because entitlement, utilized amount and the total are all calculated for that date - ask which date rather than assuming today. Entitlement figures belong to the date they were fetched for and to no other: to answer 'what is my entitlement on 2 September', or whenever the user names or changes the date, call this tool again with fieldValues containing just that application date and report the figures it returns. Never carry an entitlement figure across from an earlier date, and never state one without a tool call behind it. Use a dropdown option's text, never a code; dates in the format the discovery response states; amounts as plain numbers; yes/no fields as 'yes' or 'no'. 'Total Request' is the amount Benefit History records; PeoplesHR calculates it from the amount field(s), so leave it out unless the user explicitly wants a different total. Entitlement, Utilized Amount and Balance are never inputs. The Total Request field is one of these: it is editable on the screen, so when the user asks for a particular Total Request, put that figure here under the Total Request field name and leave the amount field(s) exactly as they gave them. It does not have to match the amount, and it must never be refused as "calculated" unless this tool itself says PeoplesHR locks it.
- `rows` (array, optional) — For benefit types claimed as rows (the discovery response sets rowsRequired and lists gridColumns instead of fields): one object per claim row, each keyed by the exact column displayName from that response. Ask the user for one row per claim - e.g. one per bill - and never invent columns. Read-only columns (Department, Entitlement, Utilized Amount and the like) are filled in by PeoplesHR and must not be sent. Each row is validated by PeoplesHR as it is added, and a rejected row stops the application with the reason given.
- `comment` (string, optional) — The applicant comment for this application. Only required when the discovery response's commentMandatory is true - check that rather than always asking. If showComment is false for the resolved benefit type, omit this entirely.
- `confirmed` (boolean, optional) — Set true only after the user has seen the preview this tool returns (the benefit type, every resolved value, entitlement/utilized/balance, the Total Request amount, any totalWarning, amountWarning or balanceWarning, the comment, and any confirmMessage from PeoplesHR) and has explicitly agreed to submit it. Must be sent together with previewDigest. Omit or set false to preview without submitting - safe to call repeatedly while they are still deciding.
- `previewDigest` (string, optional) — The previewDigest value from the preview response the user actually saw, copied verbatim and sent alongside confirmed:true. It binds the confirmation to those exact figures: if their entitlement or utilized amount has moved since, the tool returns a fresh preview instead of submitting. Never invent or reuse an older value - always copy the one from the most recent preview response.
- `removeAttachments` (array, optional) — File names to leave out of this application, exactly as shown in the preview's attachments list or as attached in the chat. Attachments are never passed as arguments: files the user attaches in the chat are picked up automatically, checked against the benefit type's own allowed file types, maximum size and count, and uploaded when the preview is built. Use this when the user asks to remove an attachment before confirming (it is deleted from the application), or to continue without a file the tool rejected. Keep passing the same list on every later call for this application, including the confirmation - otherwise a removed file still attached in the chat is uploaded again. Attachments cannot be removed after submission.
- `attachmentSessionKey` (string, optional) — The attachmentSessionKey value from this tool's most recent response for this application, copied verbatim. Attachments are staged on PeoplesHR under this key before submission, so it must be sent on every later call for the same application - including the one with confirmed:true - or the staged files will not be found. Leave it out on the first call, and leave it out again if the benefit type changes.
- `replaceAttachments` (boolean, optional) — Set true when the user wants the file(s) they have just attached in the chat to REPLACE the document(s) already on this application - "change the document to this", "use this one instead", "replace the attachment". The tool then deletes whatever is attached but not re-attached in the chat, uploads the new file(s), and lists what the application ends up with. It is ignored when no usable file is attached, so it can never leave the application with nothing. Leave it out to simply add a file alongside the existing ones.
- `totalRequest` (number, optional) — The Total Request figure, when the user asks for a particular one ("change the total request to 150", "keep the amount as 200 and the total as 150"). The Benefit Application screen lets this figure be typed over: PeoplesHR fills it in from the amount field(s), but whatever it holds at submission is what Benefit History records, and it does NOT have to match the amount. Pass the figure here and leave the amount field(s) in fieldValues exactly as the user gave them - never change an amount to match it, never offer to change the amount instead, and never answer that the two are linked or that the total cannot be changed. Leave this out unless a particular total was asked for. If PeoplesHR locks the figure for that benefit type, this tool says so itself.
